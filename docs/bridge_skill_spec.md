# Bridge Skill 需求规格

> 此文保留 0.1 版本设计记录。当前实现以 [0.2.0 主题探索规格](bridge_explore_spec.md) 为准。

## 1. 目标

创建一个可移植的 Agent Skill（当前通过多客户端插件交付，详见 `docs/bridge_plugin_spec.md`），帮助 Agent 对指定代码仓库进行有源码证据的理解分析，并生成可直接打开的 `.bridge/index.html`。页面必须复现 `prototype/rpent.html` 的信息架构、视觉风格和渐进式交互，而不是由 Agent 针对每个仓库重新设计。

默认分析当前目录，也接受用户指定的仓库路径。分析过程只读取目标源码，仅在目标仓库 `.bridge/` 写入分析产物，不修改源码。

## 2. 参考原则

参考 `Understand Anything` 的架构方法：稳定 Dashboard 与分析数据分离、结构化数据校验、源码访问有明确边界。Bridge 不复用其深色金色主题、React 技术栈或图谱优先交互。

`prototype/rpent.html` 是唯一页面原型；`.bridge/base-structure.png`、`.bridge/cli-flow.png`、`.bridge/dashboard-flow.png` 是视觉对照基准。

## 3. 功能范围

### 3.1 仓库分析

- 优先通过 Git 获取文件清单，非 Git 仓库使用受控目录遍历。
- 应用默认排除、Git 忽略和 `.bridgeignore`，始终排除 `.bridge`、VCS 元数据、依赖、构建产物、二进制和常见密钥文件。
- 为扫描保留的每个文本文件提供真实分类与职责摘要，不能将原型收录数量当作上限。
- 保存扫描范围、排除和失败警告，不承诺发现所有动态调用。
- 从真实入口发现有学习价值的调用主线；视图由仓库决定，不强行制造 CLI 或 Dashboard。

### 3.2 页面

- 顶栏：Bridge 标识、真实仓库名、commit、真实文件总数、仓库 VS Code 链接。
- 侧栏：结构视图与调用视图分组；基础文件树为主，调用视图可逐项增加。
- 基础文件树：目录、文件分类、入口、职责摘要、文件详情、搜索、展开收起；不得出现调用箭头或关系入口。
- 调用视图：按阶段组织，卡片折叠时显示路径、类/函数、对象、行号、关键调用行和 VS Code 精确链接。
- 箭头：区分直接调用、实例调用、HTTP/SSE、回调与纯流程继续，并标出实际调用形式。
- 渐进源码：展开后显示真实源码、行号、高亮和独立 Agent 注释；回调需要同时呈现绑定位置。
- 保留搜索、全部展开收起、空状态和窄屏文件详情行为。
- 输出为静态单文件 HTML，无需安装依赖或启动服务器。

### 3.3 数据与证据

`analysis.json` 至少包含：

- 项目元数据：名称、绝对根路径、目标仓库 commit（非 Git 快照为 null）、分析时间、文件总数。
- 递归节点：目录/文件、路径、7 类分类、入口、职责和子节点。
- 调用视图：名称、说明、阶段及有序步骤。
- 代码证据：路径、角色、符号、起止行、关键行、源码和 Agent 注释。
- 调用步骤：证据引用、调用类型、调用表达式、对象/类型、可选附加证据。

不另建与调用步骤重复的 `relations` 数据源。文件树与调用导航均从同一份分析数据派生。

## 4. 非目标

本期不实现增量分析、常驻后端、在线编辑器、完整动态调用追踪、VS Code 扩展、自动修改目标源码或自动启动外部应用。

## 5. 文件规划

```text
skills/bridge/
├── SKILL.md
├── assets/dashboard.html
├── references/analysis-workflow.md
├── references/data-contract.md
├── references/prototype-contract.md
└── scripts/
    ├── scan-repository.mjs
    ├── validate-analysis.mjs
    └── render-dashboard.mjs
```

脚本仅使用 Node.js 标准库。skill 使用标准 frontmatter，不加入宿主专属字段、变量或安装行为；宿主声明和安装逻辑放在插件交付层。

## 6. 质量门槛

### 6.1 确定性校验

发布前必须验证：

- 字段、枚举、ID、树和证据引用完整有效。
- 项目根路径和 commit 与扫描结果一致，非 Git 快照不得继承外层仓库 commit。
- 扫描保留文件均有摘要和分类，路径不能逃逸目标根目录。
- 代码范围、关键行和源码与对应仓库文件完全一致。
- 每个调用视图和阶段有实际内容，证据没有孤立或伪造引用。
- 验证失败时阻止生成 Dashboard，不通过自动删除错误字段伪装成功。

### 6.2 原型一致性

最终必须在真实 skill 生成物上核对：

- 基础树为三栏，调用图为两栏；侧栏分组、字体、颜色、间距和组件结构与原型一致。
- RPent 样本的 CLI 为 3 阶段 17 个代码位置，Dashboard 为 3 阶段 29 个代码位置。
- 所有节点具备应有字段；展开后有源码与注释；基础树无调用关系。
- 搜索、展开、视图切换、文件详情及窄屏交互可用。
- VS Code URI 的路径、行、列正确；未实际启动 VS Code 时不得声称验证了外部应用跳转。

### 6.3 真实调用

在新的 Kimi Code 会话中通过真实 `/bridge` 调用，对 RPent `d903f38` 的临时归档副本进行分析。不能使用主会话手工生成数据后冒充真实调用结果。若真实发现或调用受阻，必须明确报告，不能仅以单元或脚本检查替代。

## 7. 交付与版本管理

需求规格、可工作的 skill、评测修正分阶段检查并提交 Git。所有生成物和临时评测输入放在 `.bridge/` 或系统临时目录，不提交用户无关改动。最后一步是重新阅读本规格，并在真实生成物上完成页面风格与内容完整性核对。
