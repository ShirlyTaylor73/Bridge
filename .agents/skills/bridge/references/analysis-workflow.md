# 仓库分析工作流

## 1. 准备与扫描

确认目标是可读目录，Node.js 可用，且允许在目标 `.bridge/` 写入产物。定位当前 skill 根目录，后续脚本均从该目录调用，不要求目标仓库安装依赖。

```bash
node "<skill-root>/scripts/scan-repository.mjs" "<repository-root>"
```

读取 `.bridge/scan.json`，向用户简要说明扫描规模和警告。扫描结果是本轮分析清单；项目根路径和 commit 以其中的 `project` 为准，非 Git 快照使用 `null`，不要读取外层仓库的 commit。不要读取扫描器标记为 secret 的文件，不要跟踪符号链接，也不要把依赖或构建产物纳入语义分析。

大型仓库按顶层目录或关联模块分批阅读和记录摘要。中间结果可放 `.bridge/intermediate/`，但最终只发布通过校验的完整数据。失败不能静默改成少量示例文件；明确说明无法覆盖的部分并停止发布“完整”结果。

## 2. 文件树语义

逐批阅读实际源码、配置和文档，为 `scan.json.files` 的每一项建立文件节点。摘要回答“它在仓库中承担什么职责”，不要只把文件名换成一句话。按主要职责选择 7 类分类，并标记真实入口。

目录节点由保留文件路径组织，目录摘要反映实际子模块职责。顶层目录可以默认展开，深层目录默认收起。所有节点 ID 使用路径派生的稳定值。

这一阶段只建立结构理解，不把 import 关系画到基础树，也不根据文件名虚构调用视图。

## 3. 发现调用主线

从 manifest、命令注册、应用初始化、HTTP 路由、浏览器入口和真实任务入口入手。选择能帮助用户理解主要执行过程的少量视图，每个视图回答一个完整问题。仓库没有 Dashboard 时不创建 Dashboard 视图，没有 CLI 时不创建 CLI 视图。

沿实际代码追踪调用：

- 区分工厂返回、实例方法、模块函数和纯流程继续。
- HTTP、SSE 与其他协议保留客户端和接收端，不能用普通 calls 掩盖边界。
- 回调同时阅读调用点、注入/绑定位置与实际目标。
- 对动态分派、反射、字符串路由等无法确认的关系，不标记为已证实调用。可在最终警告说明分析边界。
- 不为覆盖所有 import 而生成巨大图；调用视图是有证据的学习主线，完整文件覆盖由基础树负责。

## 4. 提取源码与注释

按数据契约记录证据。使用读取工具的真实行号，并再次从磁盘核对起止范围。`code` 不包含省略号，不自行格式化，不把多段不连续代码拼成一段。关键行必须展示真正发起调用、定义目标或解释流程的代码。

Agent 注释补充仅看关键行难以理解的信息，例如对象从哪里来、为何延迟导入、哪个共享状态被传递、异步/线程/清理语义。注释与源码分开存放，不写进 `code`。

同一证据可以复用于多个视图。新增视图只增加结构化视图数据，不修改基础树或页面资产。

## 5. 校验与渲染

```bash
node "<skill-root>/scripts/validate-analysis.mjs" "<repository-root>"
node "<skill-root>/scripts/render-dashboard.mjs" "<repository-root>"
```

验证失败时修正 `analysis.json` 或重新扫描。不得修改扫描清单逃避覆盖检查，不得删除无效证据来隐藏未完成视图，不得绕过验证直接注入 HTML。

渲染器再次执行验证，成功后生成 `.bridge/index.html`。保留 `scan.json` 和 `analysis.json` 供追溯。

## 6. 最终验收

在真实浏览器打开生成 HTML，阅读 `prototype-contract.md` 并逐项检查：

1. 文件树覆盖扫描清单，目录/文件职责和计数真实，结构视图没有关系线。
2. 每个调用视图的阶段、代码位置、调用形式、关键行、源码和注释完整；回调绑定可展开查看。
3. 搜索、目录展开、源码展开、视图切换、文件详情和窄屏行为可用。
4. 页面布局、颜色、字体、间距和组件与原型一致，未因仓库内容改变主题。
5. VS Code 链接指向目标仓库的正确绝对路径和关键行。未实际启动 VS Code 时只报告 URI 校验。

发现问题先修复再重新运行真实浏览器验收。最终答复包含 HTML 路径、文件数、视图表、警告和未实测的边界。
